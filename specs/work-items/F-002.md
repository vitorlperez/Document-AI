# F-002 - Authentication and invitations foundation

**Status:** done

## Source and outcome

- Source specification: [001-mvp-document-intelligence.md](../001-mvp-document-intelligence.md), sections 3, 4, 6 (F1), 7, 9, 11, 12, 13, 14 and 15; [ADR-0001](../adr/0001-authentication-and-invitations.md).
- User outcome: verified users can establish a safe browser session, create an organization or accept an invitation, and Owners can invite Admins or Members without weakening tenant isolation.
- Non-goals: Google Drive OAuth; password, SSO and MFA flows; Next.js UI; email/domain configuration in vendor dashboards; production secret provisioning; granular folder permissions; document features.

### Impact and failure states

- **Data:** add `auth_identities`, `user_sessions`, `membership_invitations`, membership deactivation timestamp and PostgreSQL uniqueness/indexes. Secrets are hashes only.
- **API:** add AuthKit login/callback/logout, authenticated `GET /me`, organization creation and Owner-only invitation endpoints. Failure responses are generic 401/403/404 and reveal neither session nor invitation details.
- **Authorization:** routes authenticate a server session, then resolve active membership for the target organization. No request header, browser field, WorkOS organization or role claim is trusted as authorization.
- **Observability:** emit structured event names/outcomes/timing only; never session cookies, authorization codes, invitation tokens, provider access/refresh tokens or full invitation URLs.
- **Performance:** local request baseline under 200 ms for session lookup and authorization against a small dataset, excluding a remote WorkOS redirect/code exchange. The exact measured probe is recorded before completion.

## Acceptance criteria and test matrix

| Criterion | Test layer | Evidence |
| --- | --- | --- |
| Given a verified AuthKit identity, when its callback is accepted, then exactly one local user and external identity exist and a secure opaque session is issued. | API + PostgreSQL integration | Idempotent callback/session test; database stores hashes only. |
| Given no valid active server session, when a protected endpoint is requested, then it returns 401 without implementation or secret details. | API | Missing, expired, revoked and altered cookie tests. |
| Given an authenticated user without an active membership, when they create an organization, then they become its Owner and an audit record is written. | API + PostgreSQL integration | Positive creation and audit test. |
| Given an Owner, when they invite an Admin or Member, then a single pending invitation is stored, a delivery port receives the raw token once, and only its hash is persisted. | API + PostgreSQL integration | Create and inspect/redaction test. |
| Given an Admin or Member, when they attempt to invite, revoke or alter members, then the request is denied and changes nothing. | Authorization negative | Cross-role test. |
| Given an invitation, when a different verified email accepts it, then it fails without creating membership; the matching verified email may accept it once. | API + PostgreSQL integration | Matching/mismatching email test. |
| Given a revoked, replaced, expired or altered invitation token, when accepted, then it is rejected without data disclosure. | Unit + API | Token lifecycle test. |
| Given a user/session/invitation in organization A, when acting on organization B, then no data is returned or changed. | PostgreSQL authorization negative | Cross-tenant test. |
| Given authentication, invitation or audit events, when logs are emitted, then no token/cookie/code/e-mail payload is logged. | Unit | Structured-log redaction test. |
