# F-001 - Foundation modular monolith

**Status:** done

## Source and outcome

- Source specification: [001-mvp-document-intelligence.md](../001-mvp-document-intelligence.md), sections 7, 8, 10, 12, 14 and 15; specifically implementation step 1 (fundamentos), modular-monolith boundaries and tenant-isolation invariants.
- User outcome: a developer can start the product locally with a repeatable API, database migration path and explicit multi-tenant domain boundaries. Future features can create and authorize organization-scoped records without bypassing a common scope guard.
- Outcome for this feature: establish the runnable modular-monolith foundation only: service skeleton, PostgreSQL connection and migrations, `identity`, `organizations` and `audit_usage` domain primitives, organization-scoped repository conventions, health/readiness endpoints, structured observability and a local Docker Compose environment.
- Non-goals:
  - No external authentication provider, login, session, password, magic link, invitation delivery or public account-creation flow.
  - No Google OAuth, Google Drive API client, credential storage or source/workspace-folder implementation.
  - No ingestion, vector search, LLM, background worker, Redis/Celery, user-facing product UI, billing or rate limits.
  - No production deployment, cloud account, secrets manager or provider-specific IaC.
  - No endpoint may pretend that an unauthenticated caller is a real product user. Identity/role-aware application services are exercised through internal test fixtures only until F-002 selects authentication.

### Impact and failure states

- **Data:** initial Alembic migration creates `organizations`, `users`, `memberships` and `audit_logs`; foreign keys and unique constraints make duplicate membership and orphan audit records impossible.
- **API:** only `GET /health/live` and `GET /health/ready`. Liveness verifies process availability; readiness verifies the database with a bounded query and returns an explicit unavailable result when it cannot connect.
- **Authorization:** no HTTP authentication is added. Organization and membership authorization rules exist in application services/repositories and are covered by direct integration tests. `workspace_folder_id` is not introduced because no workspace resource exists yet.
- **Observability:** request and database-readiness logs are structured and contain correlation/request id, route, status and elapsed time; they must not contain database URLs, credentials, token-like values or user content.
- **Failure states:** invalid configuration fails startup with a clear non-secret error; unavailable database makes readiness fail without leaking connection details; duplicate organization membership returns a typed domain conflict; cross-tenant access produces no record/data disclosure.
- **Performance budget:** health liveness has no database I/O; database readiness uses one bounded query (target local p95 under 200 ms). A performance harness is not yet available, so this is recorded as baseline instrumentation evidence, not a release gate.

## Acceptance criteria and test matrix

| Criterion | Test layer | Evidence |
| --- | --- | --- |
| Given a valid local configuration and an initialized database, when the API starts, then `GET /health/live` returns 200 without requiring a database query. | API integration | Focused endpoint test plus structured request log assertion. |

| Given an audited internal membership change, when the action succeeds, then an audit record contains actor reference, organization id, action and timestamp but no secrets or document content. | Unit + database integration | Schema/repository test and log/audit payload assertion. |

| Given the initial migration is applied to an empty PostgreSQL database, when it is upgraded, then all four foundation tables, tenant keys and declared uniqueness constraints exist. | Migration integration | Fresh-database migration command and schema inspection. |

### Implementation notes for test design

- Use a real ephemeral PostgreSQL instance/container for migration and repository tests; SQLite is not evidence for PostgreSQL constraints or the future pgvector-compatible deployment.
- Test fixtures may create internal `User`/`Actor` objects but must not add a bypass header, fake production login endpoint or external-provider abstraction.
- A database transaction/session must be created by the common infrastructure boundary; tests should prove a caller cannot omit organization scope on tenant-owned repository methods.
- The implementation owner supplies local commands; the test engineer records focused results first, then the relevant complete backend suite. The feature validator reruns them independently.
