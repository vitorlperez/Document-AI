# F-025 - Conversa persistente e retrieval explicável

**Status:** done

## Source and outcome

- Source specification: `specs/001-mvp-document-intelligence.md` F4, sections 7, 10 and 11; user-reported retrieval and conversation regressions.
- User outcome: questions against a selected, indexed workspace produce an explainable result; the chat preserves each submitted message while the composer is edited; operators can distinguish unavailable/indexing/retrieval/generation outcomes without exposing prompts, embeddings, tokens or document content.
- Non-goals: a LangChain/LangGraph dependency, autonomous tool calling, cross-workspace/company answers, changing embedding provider/model, a database migration, persistent server-side chat history, or a vector-index rollout. A future agent may call this retrieval service only through a server-bound scope.

## Decisions

| Decision | Owner | Status | ADR / rationale |
| --- | --- | --- | --- |
| Keep retrieval deterministic and scoped; do not introduce LangChain/LangGraph in this corrective feature | Product + implementation | approved | One retrieval tool and fixed path do not require agent orchestration; scoped service remains the future tool boundary |
| Return explicit stable retrieval statuses while preserving `insufficient_evidence` as the safe user outcome | Product + implementation | approved | Makes empty/incomplete indexing, low relevance and invalid generation actionable without leaking content |
| Snapshot submitted chat messages in the client and retain a local conversation only for the current browser view | Product + implementation | approved | Fixes mutable message rendering without changing data retention or server ownership |
| Use a conservative lexical rescue for strong exact matches, retain semantic ranking and cited-answer gate | Product + implementation | approved | Reduces false negatives while retaining source/citation constraints; threshold is tested rather than disabled |

## Validator report

- Blocking: none. The initial review found that the Responses REST envelope was parsed as SDK-only `output_text`; it was corrected to read `output[].content[type=output_text].text`, with a raw-envelope regression test before revalidation.
- Important: none.
- Suggestions: add browser-level chat interaction coverage once the frontend has an appropriate component/E2E test harness.
- Independent evidence: validator inspected the final diff, confirmed status-to-UI mapping, immutable composer/message snapshots, allowlisted logs, scoped candidate queries and cited-answer gate. It independently ran 36 focused tests, the full suite (166 passed, 6 skipped), Ruff, frontend build and `git diff --check`.
