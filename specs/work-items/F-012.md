# F-012 - Aceite web seguro de convites

**Status:** done

## Source and outcome

- Source specification: ADR-0001 and `specs/001-mvp-document-intelligence.md` identity and membership flows.
- User outcome: a recipient can open the invitation URL, authenticate if needed, explicitly accept a valid invitation and land in the invited Company instead of receiving a frontend 404.
- Non-goals: exposing invitation details before authentication, accepting an invitation implicitly, changing invitation token lifecycle, or adding a new identity/email provider.

## Decisions

| Decision | Owner | Status | ADR / rationale |
| --- | --- | --- | --- |
| Login return path | Implementation owner | Approved | The backend accepts only a narrow invitation path as `return_to`, stores it in a short-lived HttpOnly cookie and validates it again before redirecting; this prevents open redirects. |
| Acceptance interaction | Product | Approved | Opening a link presents an explicit accept action; only the existing authenticated acceptance API creates the membership. |

## Acceptance criteria and test matrix

| Criterion | Test layer | Evidence |
| --- | --- | --- |
| Given an unauthenticated recipient opens a valid-format invitation URL, when they select sign in, then AuthKit returns only to that same invitation route after authentication. | API + UI | Redirect test, route build and browser check |
| Given an authenticated recipient opens an invitation URL, when they explicitly accept it, then the existing API creates their membership and the UI routes to the Company UUID. | API + UI | Existing token lifecycle test plus route build |
| Given an invalid, expired, already-used or mismatched-email token, when acceptance is requested, then the UI shows a safe failure and no membership is created. | API + UI | Existing negative acceptance tests; UI error state review |
| Given a forged `return_to`, when login completes, then no external redirect is possible. | API | Redirect negative tests |
