# F-023 - Ingestão resiliente e concorrente do Google Drive

**Status:** done

## Source and outcome

- Source specification: `specs/001-mvp-document-intelligence.md` F3/F4; F-016.
- User outcome: large Google Drive synchronizations finish extraction faster and recover safely from transient OpenAI `429` responses, without compromising snapshot atomicity or document scope.
- Non-goals: a staged fan-out/fan-in Celery architecture, parallel database writes, parallel embedding calls, a new external provider, or a schema change.

## Decisions

| Decision | Owner | Status | ADR / rationale |
| Use bounded threads only for remote file download/extraction; retain deterministic output order and write to the database from the worker thread only | Product + implementation | approved | The current Google client is synchronous; this improves I/O throughput without sharing SQLAlchemy sessions across threads |
| Keep Drive listing paginated and sequential | Implementation | approved | Page tokens and recursive folder traversal establish ordered discovery dependencies |
| Use 16-chunk sequential embedding batches with bounded exponential backoff and `Retry-After` support | Product + implementation | approved | Limits burst size for whole-Drive syncs and recovers transient throttling without parallel OpenAI traffic |
| Preserve the uncommitted snapshot until extraction, embedding and projection all succeed | Security + implementation | approved | Existing F-016 rollback invariant remains intact |
| --- | --- | --- | --- |

## Acceptance criteria and test matrix

| Given a discovered set of eligible Google files, when extraction begins, then no more than the configured bounded number download/extract concurrently and the returned document order remains deterministic. | Unit | Passed: blocking-client test reaches exactly 6 active reads and verifies stable ID order. |
| Given an unsupported file or a per-file extraction failure, when concurrent extraction runs, then it retains its current explicit per-document status and does not cancel other files. | Unit | Passed: unauthorized, extraction-error, unsupported and successful siblings are all represented. |
| Given an embedding request returns 429 with `Retry-After`, when a batch is embedded, then the worker retries only that batch after the indicated/bounded wait and does not double-record local token usage. | Unit | Passed: 17 chunks make calls of 16, retried 16, then 1; one usage record is asserted. |
| Given the retry budget is exhausted, when embedding remains throttled, then the existing worker rollback/retry and terminal `embedding_failed` behavior preserves the prior snapshot. | Unit + existing F-016 regression | Passed: Celery task test asserts rollback and terminal status; F-016 snapshot regression remains green. |
| Given a large Drive sync, when it runs, then Drive extraction has at most 6 concurrent remote requests and OpenAI embedding remains sequential at 16 chunks per request. | Unit/configuration review | Passed: a requested 100 workers is capped at 6; provider batches at 16 without parallel embedding calls. |
